# Laravel

- Functions returning `void` do not need `@return void` in their PHPDoc.
- When using the `==` operator for comparison, place constants on the left side before the variable, e.g. `'valid' == $submissionStatus`.
- For null checks: avoid `null == $var` (loose equality also matches `""`, `0`, `false`, `[]`). Prefer `isset($var)` / `!isset($var)` for "set and not null" or "unset or null".
- For testing, allow Direct Model Creation instead of always requiring a Factory in test files.
- In test files where a seeder populates a model (e.g. MarketSeeder for Market), do not flag `Model::first()` as potentially null or suggest `firstOrFail()` or factories.
- Do not flag missing UUID validation for fields that are listed in the `$uuids` array property of request classes extending `AppRequest`. The `$uuids` property automatically validates UUID format in `prepareForValidation()` method, so explicit UUID validation is not needed for these fields.
- (High) Do not require imports for classes that are within the same namespace. Only flag missing imports when the class is in a different namespace.
- Do not require a TABLE constant for a model's own table name unless the table name is used elsewhere (e.g. by other models in relationships). A string literal for `$table` in a single model is acceptable.
- When performing multiple Eloquent operations in a loop, if only one entry can be invalid: throw a specific exception for that entry and catch it inside the loop so that the remaining operations can continue (e.g. log or collect the failure and proceed with the next iteration).
- It is acceptable for columns intended for limited values (like enums) to use plain int/string types without explicit database constraints.
- For services without constructor arguments, prefer resolving/instantiating them via the Laravel Service Container (e.g. `app(MyService::class)`) rather than calling `new MyService()` directly. Only flag this in code that is being modified, not in existing unmodified code (the codebase has mixed usage).
- Before reporting that a class accesses a relationship (e.g. `$model->relation->property`) without a null check or that the relationship might not be loaded: find all call sites and verify whether the caller already loads that relationship (e.g. via `loadMissing()`, `with()`, or eager loading). Only flag the issue if no caller guarantees the relationship is loaded.
- (Medium) Before requiring/keeping a re-fetch or existence check for an event or other target resource id inside an Action (e.g. `findEventOrFail`, `firstOrFail` on the same id): inspect HTTP/controller (or other) call sites. If the caller already validated access and found the resource (e.g. `getAccessibleEventIdQuery(...)->firstOrFail()`, policy + scoped query, route-model binding that guarantees existence), flag the Action-side re-check as redundant and prefer removing it. Still require the Action-side check when any call site does not guarantee the resource, or when the Action is a shared entry used outside that validated path.
- Prefer a dedicated helper class/file for very specific helper logic (e.g. sequence-format parsing) rather than adding many domain-specific methods to a general helper like AppStr; keep general helpers for broad string/formatting utilities.
- For services that handle both admin and customer flows, avoid methods that must "guess" context such as `orgId`. Prefer separate, intention‑revealing entry points (for example, dedicated Ad/Cs services or methods) where admin flows always pass `orgId` explicitly and customer flows derive context only in clearly scoped customer-specific code, with any shared logic factored into a dedicated shared service.
- Before flagging a property/method as unused/dead on a class that extends a parent or mixes in a trait: open the parent/trait body and grep for the symbol — inherited consumers (parent methods reading `$this->prop`, trait methods called via `$this`, base-class lifecycle hooks) are not visible in the child file.
- (Medium) Parent delete guarded by child `exists()` (or equivalent related-row check) then `$model->delete()`, when a DB FK restrict/no-action blocks orphan children: flag TOCTOU race if the check+delete is not inside a transaction that `lockForUpdate()`s the parent before re-check. Concurrent child insert after `exists()` can still hit FK and surface as 500. Also require catching `QueryException` FK restrict (PostgreSQL `23503` / SQLSTATE `23000`) and returning the same business failure (`success` false / 422 msg) as the pre-check path; rethrow other DB errors. Do not require this when there is no FK restrict path (cascade/set-null) or the operation is not concurrent-sensitive.
